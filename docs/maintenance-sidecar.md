# 独立维护容器：已实现的调度与回写原型

这是已在独立部署中运行的实现总结及脱敏参考源码，位于 `contrib/maintenance-sidecar/`。它与 #453 的主程序内置维护代理方案分开：不修改主程序转发调度代码，复用官方 provider 插件处理维护操作，把余额结果交回官方 usage 接口落库并更新调度缓存。

本 PR 提交可审阅的原型和隔离测试，不接入默认构建、默认镜像或自动安装流程。当前适配范围仅 Loomy、小浣熊，数据库结构和插件回调以已验证的 3.4.2 契约为基础。它还不是跨版本即装即用的官方功能。

## 已实现的行为

| 组件 | 行为 |
|---|---|
| 独立调度 | SQLite 持久任务队列，同账户互斥、同操作去重、全局/平台/操作并发上限、随机启动间隔、冷却和有界自动入队缓冲 |
| 分操作出口 | 每个平台的签到、余额查询、凭证维护分别选择直连、自动节点或固定节点；不写模型请求的账户代理绑定 |
| 正余额优先 | 自动入队及实际派发都优先已知正余额；同类任务继续按队列顺序处理，未知余额保留独立查询机会 |
| 零余额退出 | 成功确认零积分后退出周期查询；跨到次日零点也不重新扫描零余额，等待之后的一次成功签到 |
| 签到后补查 | 签到成功创建或复用同账户的高优先级余额任务；成功得到正余额后恢复周期查询，仍为零就继续等待下次签到 |
| 凭证维护 | 对官方确实支持续期的凭证，在到期前 5 分钟安排处理，较早到期优先；不把 Loomy/IAM 查询当作续期 |
| 节点巡检 | 分散排期、定时 HTTPS 连通检测、连续失败隔离、隔离节点复测、连续成功恢复；人工停用独立保存，不被自动恢复覆盖 |
| 运行页面 | 总览、实时账户、队列、记录、调度设置、节点管理；分页接口、后台快照、加载/错误/空状态及响应式布局 |

签到有每日时间窗口、每天最大尝试次数和失败间隔。当前原型的时间边界采用 `Asia/Shanghai`，不把宿主机时区作为签到日期。原型默认暂停，自动任务默认关闭；重启后同样暂停，操作员需要明确恢复。只判断 JWT 过期字段和可续期能力，不声称能续期所有账号。

### 零余额的状态流转

```text
已知正余额 --周期查询成功为 0--> 等待下次签到
等待下次签到 --00:00--> 仍等待签到，不创建余额扫描任务
等待下次签到 --签到失败--> 继续等待，按签到策略处理
等待下次签到 --签到成功--> 余额补查
余额补查 --成功 > 0--> 正余额周期队列
余额补查 --成功 = 0--> 等待下次签到
余额补查 --失败/超时--> 保留旧记录，单独记录错误和冷却
```

余额是否确认以成功查询为依据；未知余额、无限量、负值不会被当成“已确认零余额”。新签到时间必须晚于上次成功余额时间，不能拿签到前的零余额跳过签到后的查询。手动查询作为明确操作保留，零余额自动退出规则不拦截手动请求。

“查询间隔”是允许进入队列的最早时间，不是完成时间承诺。正余额优先也不是严格的跨平台公平调度：两平台仍共享余额总并发，平台保底配额尚未实现。

## 余额为什么要经过官方接口

```text
维护队列
  -> 官方 GET /api/accounts/usage?id=ACCOUNT
  -> 官方插件 usage.query 的可选桥接适配器
  -> 独立容器 /internal/usage
  -> 选维护节点 -> 原始 provider 插件 usage.query
  -> 将 usage 结果返回官方主程序
  -> 官方主程序保存 account_usage_records 并更新调度/额度缓存
```

仅更新数据库余额表不能保证转发调度立即采用新余额。因此自动余额任务调用官方 usage 接口；参考适配器只转发 Loomy/小浣熊的 `usage.query`，模型及其他帧原样交给原插件。插件响应的并发帧按 ID 返回，超容量明确报错，不回退直连。

**原始主程序二进制保持不变不等于完全零集成。** 该路径仍需要配置、启用 usage 桥接适配器，并保留原官方插件。参考源码提供 `bridge/main.go`，但没有自动替换插件、编辑插件索引、关闭官方调度或注册桥接的安装脚本；这些需维护者决定正式接入契约。插件自动更新也可能覆盖本地适配层，这部分尚未做成正式生命周期管理。

签到和支持续期的凭证维护复用 provider RPC，相关回调按账户范围条件更新；这两条路径目前仍依赖共享数据库及加密密钥，不是纯 HTTP API 的无状态服务。余额代码还保留了早期数据库写入辅助函数，当前周期余额执行路径不调用该函数。小浣熊“未确认入账”时额外读取当天账单证据，不因保活或空响应就记作积分领取成功。

## 节点与页面

默认健康策略为每 15 分钟检测正常节点，首次失败后约 60 秒确认，连续 2 次失败隔离，隔离后每 5 分钟复测，连续 2 次成功恢复。检测并发最多 3，排期加入错峰和抖动。策略可在页面调整，自动检测默认关闭。

自动及固定出口都会排除隔离节点；固定节点坏了也不会暗中换直连。无可用节点时保留任务，不制造账户错误。当前 HTTPS 检测只能说明所选检测站点连通，不能证明 Loomy/小浣熊一定接受该出口，也不能把上游 403 直接判为死号。

节点地址、鉴权内容不会由节点列表 API 回显，页面仅展示名称、延迟、最近/下次检测、连续失败/成功次数、人工状态和自动隔离状态。订阅解析、订阅定时更新/续费不在本次实现范围。

UI 使用现有原型的轻量 HTML/CSS/JS 和固定版本 Tom Select；所有资源本地提供，无运行时 CDN。Tom Select 的 MIT 许可证、来源与文件哈希保留在 `vendor/` 和 `vendor-manifest.json`。本 PR 不引入第二套 React/Tailwind 依赖。

## 仍需维护者评估的问题

- 余额查询超时、上游内部错误、停用、401、402、403、429 是不同结果，均不能算成功；最新错误和上次成功余额必须同时展示，旧正余额合计不是实时可用积分。
- 现有适配器按容量拒绝而非等待，旧并发错误可能保留在主程序余额记录中；未来可改为正式的有界背压/可重试错误契约。
- 管理客户端遇到 401/403 会使本次操作失败，下一次调用再登录；目前未实现本次请求内自动重新登录重放。
- 冷却尚未按“管理登录错误 / 网络错误 / 账户错误”彻底拆开，失败次数还会拉长冷却，可能使旧余额长时间未更新。
- 当前 prototype 用 Linux amd64 的 proxychains 路径与 provider target 默认值；其他架构需要显式适配。仅支持 HTTP/SOCKS 的 IPv4 入口，不直接解析 Clash/AnyTLS 订阅。
- 数据库/插件协议升级需要重新验收；副本验证通过不能当作任意官方版本兼容性证明。
- 管理会话仅存在于内存；未实现多租户权限、跨容器高可用任务租约或无人值守重启恢复。

以上问题写入 PR 是为了让维护者看到实际边界，不能以“节点多、并发高”替代成功率和数据新鲜度。

## 可复现验证

在仓库根目录运行，仅使用临时数据库、合成账户和本地假上游：

```sh
python3 contrib/maintenance-sidecar/tests/test_policy.py
python3 contrib/maintenance-sidecar/tests/test_proxy_health.py
node --check contrib/maintenance-sidecar/ui.js
node --check contrib/maintenance-sidecar/ux.js
cd contrib/maintenance-sidecar/bridge && go test ./...
```

独立容器启动验证使用 `tests/boot_smoke.py`，必须在一次性容器中运行；脚本会在容器内创建 `/gateway`、`/key`、`/secrets` 的合成数据。测试启动真实模块、登录处理器、分页和静态资源，不运行调度线程，不调用真实 provider，不访问真实账户或模型。执行记录和部署材料不随 PR 上传。

原始部署中已观察到官方落库及调度缓存同步、零余额等待状态和节点隔离。这里不附任何真实账户数量、余额、账户 ID、域名、IP、订阅链接、密钥、数据库、截图或生产日志；成功的隔离验证只证明所列分支，不能证明所有上游随时可用。

## 与已有 PR 的关系

#453 提供主程序内置的维护出口和有界调度能力；本 PR 提供外置运行原型及其实现经验，不重复修改该 PR 的主程序文件，也不替它做兼容性或合并承诺。希望维护者先评估哪些职责应保留在 host、哪些应成为可选外置 worker，再确定正式接口。
